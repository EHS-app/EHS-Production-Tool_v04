# Overview

This project is a pnpm workspace monorepo serving as an internal stage-tech tool for EHS Rigging Load Report. Its primary goal is to optimize calculations and inventory management across various event production disciplines such as Rigging, Lighting, LED Screens, and Stage. Key functionalities include load calculation, DMX management, pixel mapping, stage design, and crew management. The application offers secure, invitation-only access for internal users via Clerk, alongside a Freelance Portal enabling producers to share project briefings and freelancers to manage gigs, availability, and earnings. The overarching business vision is to streamline event production workflows and enhance efficiency for both internal teams and external collaborators.

# User Preferences

- **Internal Tool**: This is an internal tool, so there is intentionally no public landing page.
- **Open Sign-Up**: Anyone can create an account from the sign-in screen via the Sign in / Sign up tab toggle.
- **Google Sign-in**: Visible on the production sign-in page (the auth instance currently has email/password disabled, so Google is the active sign-in method on prod). Email/password sign-in can be re-enabled from the Auth pane in the Replit Workspace toolbar.
- **No Client-side Credentials**: Admin passwords should not touch the browser.
- **Development Auto-sign-in**: In development, the preview should auto-log the user in as Admin to avoid manual credential entry on reloads. This functionality must be strictly gated by `NODE_ENV` / `import.meta.env.DEV` and not leak to production builds.

# System Architecture

## Monorepo Structure
- **Tooling**: pnpm workspaces
- **Language**: TypeScript 5.9
- **Package Manager**: pnpm
- **Node.js**: Version 24

## API and Data
- **API Framework**: Express 5
- **Database**: PostgreSQL with Drizzle ORM
- **Validation**: Zod and `drizzle-zod`
- **API Codegen**: Orval, from OpenAPI specifications

## Build and Deployment
- **Build Tool**: esbuild for CJS bundles
- **Deployment**: Supports GitHub Pages via `BASE_PATH` environment variable

## Authentication
- **Provider**: Clerk for sign-in, user management, and role-based access control.
- **Auth Screen**: Unified card with EHS logo, dynamic product subtitle, role toggle, sign-in/sign-up tabs, and an integrated Clerk widget.

## UI/UX and Features
- **Frontend**: React single-page application built with Vite.
- **Theme**: Dark/light mode toggle with persistence and Clerk integration.
- **Reporting Views**: Rigging, Lighting, LED Screen, Rigg Plan, Crew, Sound, and Stage Reports providing specialized calculations, inventory management, and design tools.
- **EHS Equipment Library Picker**: Reusable modal for selecting items from a static JSON catalog.
- **Persistence**: All view states persist to `localStorage` v2, with transparent migration from v1.
- **Freelance Portal**: Dedicated interface for external freelancers covering Hub, Briefs, Gigs, Availability, Earnings, and Profile management, including iCal export and conflict warnings.
- **Production Schedule Picker**: Compact popover for managing multi-phase production schedules.
- **Internationalization (i18n)**: Custom typed i18n module supporting English and Norwegian Bokmål, with browser language detection, persistence, and locale-aware formatting.
- **Client Field**: Integrated "Client" text input in project metadata, propagated to Client Pack, Show Simulation, and Project Briefs, and surfaced in the Freelancer Portal.
- **Show Simulation Engine**: Generates printable phase-by-phase live-event simulation reports with discipline status, aggregated risks, and readiness scores.
- **Client PDF Pack Export**: Generates a single, printable client-facing PDF document with 11 numbered sections covering all project details.
- **Production Tool ↔ Portal Brief Bridge**: Enables sharing project context with freelancers via Gzip-compressed, base64url-encoded share URLs.
- **Shared Internal Database (Production Tool ↔ Portal)**: Replit-managed Postgres database storing freelancer profiles, project briefs, brief assignments, and gigs, ensuring a single source of truth for cross-app state.
- **Logistics Foundation**: Groundwork for catering, hotel, and schedule pipelines, including new profile fields and gig attributes.
- **Stage Report — Build Direction & Per-Deck Assembly Numbering**: Allows stage builds from left-to-right or right-to-left, with per-deck assembly numbering and leg counts displayed in the SVG preview.
- **Available Crew Sidebar (Production Tool, Crew Report tab)**: Producer-facing roster panel with filter chips for skills, availability status (available, pending, booked), and direct crew addition to call sheets.
- **Drawing Analyser (Rigg Plan tab)**: AI-powered extraction from PDF/image drawings for venue dimensions, stages, trusses, lighting, LED screens, and sound items, including security and motor capacity.
- **Brief Attachments**: Integration with Replit App Storage for handling brief attachments, including API endpoints for upload and view/download.
- **Crew Request Loop — First-to-Accept-Wins**: Producer can send the same brief to N freelancers as candidates. The server's `POST /briefs/:id/respond` runs inside a transaction with `SELECT ... FOR UPDATE` on the brief row, so the first accept wins and all sibling pending rows flip to `too_late`. The terminal `too_late` decision is also guarded server-side. If a winner later un-accepts (accepted → pending), siblings that were `too_late` are reopened to `pending` in the same transaction. Client surfaces a red "Filled" pill, an inline "Position filled" banner on the freelancer's brief page, and a sync-error banner with retry on transient failures. The server poll respects a 60s `FRESH_DECISION_WINDOW_MS` so freshly-made local decisions cannot be overwritten by stale snapshots.
- **Crew Request Confirm → Gig Conversion**: When a freelancer wins an accept, the same `POST /briefs/:id/respond` transaction also materialises a `gigs` row so the freelancer's calendar, the producer's booked roster, and the directory's `booked` status pill all light up. Idempotency is keyed on `(briefId, freelancerUserId)` — never on the client-supplied `acceptedGigId`, which is treated as advisory only — so a retried accept or an "acknowledge changes" re-confirm cannot duplicate gigs or be used to overwrite somebody else's gig by guessing an id (closes IDOR vector). Existing gigs in terminal statuses (`done` / `invoiced` / `paid`) preserve status on re-accept; non-terminal gigs are promoted to `confirmed`. The transaction returns the resolved gig and the assignment, and the freelancer client swaps its optimistic local gig over to the server's authoritative id. On a winner-undoing-accept (decline or pending), the same transaction tears the gig down, and the client mirrors by removing the local gig and reverting on sync failure. Multi-device convergence: `/portal/gigs` is polled every 60s; `mergeServerGigs` drops brief-linked local gigs absent from the server (gated by the same 60s freshness window so an in-flight POST doesn't flicker), preserves local edits via id match for in-store rows, and never touches local-only logbook gigs (no `briefId`). Files: `artifacts/api-server/src/routes/portalBriefs.ts`, `artifacts/rigging-load-report/src/portal/Portal.tsx`, `artifacts/rigging-load-report/src/portal/screens/BriefDetail.tsx`.
- **Crew Request Email-on-Send (Gmail)**: When the producer sends a brief, every newly-added recipient gets a Norwegian email from the producer's connected Gmail account. New-ness is detected via `.returning()` on the `onConflictDoNothing` assignment insert, so a re-save of the same brief never re-emails existing recipients. The producer's display name is resolved through Clerk; the message links to `${REPLIT_DOMAINS}/?view=portal&brief=<id>` (falls back to `REPLIT_DEV_DOMAIN` in dev). Send is fire-and-forget so HTTP responses are not blocked by mail delivery; every attempt and failure is logged with `briefId` + `freelancerUserId` (recipient address is intentionally NOT logged). RFC 822 header construction strips CR/LF from name/subject and validates the recipient address shape to block header injection from user-edited profile data. Files: `artifacts/api-server/src/lib/gmail.ts`, `artifacts/api-server/src/lib/briefEmail.ts`, wiring in `artifacts/api-server/src/routes/portalBriefs.ts`. SDK: `@replit/connectors-sdk` (Gmail connector `google-mail`).
- **Catering Aggregation (Phase B Feature 2 — Slice A: backend + producer view)**: When a producer opens a brief, a new "Catering" tab shows a per-day breakdown of confirmed crew: total meals, plus counts for vegetarian / vegan / halal / gluten-free / lactose-free, plus an allergen roster with names and roles. Updates within ~60s as freelancers accept the brief or edit their working days (no refresh needed). Server endpoint `GET /api/portal/briefs/:id/catering` is owner-only (catering is a back-of-house view that would leak other crew members' allergens to a freelancer); it joins `gigs` (`confirmed`/`done`/`invoiced`/`paid` only — `invited` are pre-acceptance shells and don't count) against `freelancer_profiles` via `leftJoin` so freelancers without a portal profile still appear in the meal total but get surfaced separately in a "Missing dietary info" nudge so the producer can chase them. Free-text `freelancer.dietary` is classified server-side into the canonical tag set via a small pure helper (`artifacts/api-server/src/lib/dietaryTags.ts`) with English + Norwegian substring matching (vegetar/vegan/halal/glutenfri/cøliaki/laktosefri/uten melk/etc). The classifier normalises both input *and* keywords through the same `normalise()` (lowercase + collapse `-_/` to spaces) so hyphenated keywords like `lacto-ovo` survive input normalisation, and a negation guard rejects matches preceded by `non/not/no/never/ikke/ingen/uten` in the immediate left-context — without it `"non-vegan"` or `"ikke vegetar"` would tag a meat-eater as vegan and the chef would under-supply normal meals (false positives are far worse than false negatives in catering). Free-text `freelancer.allergies` is split on commas/semicolons/slashes/and/og into discrete chips so the chef can cross-reference each allergen against ingredient lists. The aggregator dedupes by `(date, freelancerUserId)` via a nested `Map<iso, Map<userId, Person>>` so a freelancer with two gigs on the same brief on the same date (e.g. a recurring show with split roles) still counts as ONE meal — chefs plate per mouth, not per booking row, and dedupe also keeps React keys stable in the per-day allergen roster. Categories deliberately do NOT cascade — a vegan dish satisfies a vegetarian, but the chef plates them differently. The producer's tab is hidden for local-only briefs (no server `briefId` to query). PDF export for the venue chef is the next slice. Files: `artifacts/api-server/src/lib/dietaryTags.ts`, `artifacts/api-server/src/routes/portalBriefs.ts` (new endpoint), `artifacts/rigging-load-report/src/components/CateringView.tsx`, `artifacts/rigging-load-report/src/App.tsx` (MainView + tab + render).
- **Auto-Assign Schedules → Gigs (Phase B Slice B — Editable Working Days)**: The freelancer's gig edit modal now includes a `WorkingDaysEditor` checkbox grid letting them override the auto-computed `assignedDates` per day — e.g. a Rigging member who needs to be on-site for rehearsal too can tick that day, or a Sound member who's only on show days can untick the build days. The visible day list is the union of the gig's `startDate..endDate` range and any currently-checked dates outside that range, so editing the start/end dates never silently drops a checked day. ISO validity uses a strict shape + Date round-trip check (mirrors server-side `isValidIsoDate`) so corrupt/legacy data can't slip through. The grid is hard-capped at 90 visible day buttons via a `VISIBLE_CAP` applied to the *final* union (not just the range loop) so a producer-set monster brief with a 366-day server cap won't blow up the modal — anything past the cap or any malformed entry is preserved in the array on save and surfaced as a "+N preserved" notice in the field's subline. Toggle/Select-All/Clear-All operate on the visible set only, so the Clear-All button can't accidentally drop preserved out-of-range entries. Persists via the existing `PATCH /api/portal/gigs/:id { assignedDates }` endpoint shipped in Slice A — no new server work needed. Files: `artifacts/rigging-load-report/src/portal/screens/Gigs.tsx` (`WorkingDaysEditor` component + `GigEditor` integration). Producer-side visibility (CrewReportView pills + per-day override grid) is deferred to a future slice — it requires a new project-scoped gig endpoint and producer auth, which is out of scope here.
- **Auto-Assign Schedules → Gigs (Phase B Slice A)**: When a freelancer accepts a brief, the server-materialised gig now carries a `assignedDates: string[]` (sorted, deduped, UTC YYYY-MM-DD) computed from the brief's `project.schedule` phases × the freelancer's role, instead of just `startDate..endDate`. Default role→phase mapping (defined inline in `artifacts/api-server/src/lib/roleSchedule.ts` with a comment cross-referencing `lib/crew.ts`): Rigging/Driver = setup+downrig only; Stage/StageHand = setup+show+downrig (skip rehearsal); Lighting/LightingFOH/Video-LED/AVFOH/Sound/SystemTech/PM/Other (and any unknown role) = all four phases. Schedule expansion is timezone-stable (UTC arithmetic), capped at 366 days per phase against runaway inputs, and silently drops malformed segments rather than failing the whole accept. Falls back to startDate..endDate when the brief has no schedule object. Drizzle column `gigs.assigned_dates date[] NOT NULL DEFAULT '{}'` was already in place from Phase A so no migration was needed. Wired through both INSERT (new gig) and UPDATE (re-accept) call sites in `gigFieldsFromBrief`. Producer-side `PATCH /portal/gigs/:id` accepts `assignedDates` for future per-day overrides. Freelancer Gigs screen renders a "N working days · Mar 10, 12, 14–16" pill (contiguous-run grouping, drops year, spans cross-month with full month names); manually-logged gigs default to `[]` so the pill stays hidden. Files: `artifacts/api-server/src/lib/roleSchedule.ts` (new), `artifacts/api-server/src/routes/portalBriefs.ts` (`gigFieldsFromBrief`), `artifacts/api-server/src/routes/portalGigs.ts` (`normaliseGig` + PATCH allow-list), `artifacts/rigging-load-report/src/portal/lib/portalStorage.ts` (Gig type + `gigFromBrief`), `artifacts/rigging-load-report/src/portal/Portal.tsx` (`normalizeGig` server→client coercion), `artifacts/rigging-load-report/src/portal/screens/Gigs.tsx` (`emptyGig`, `summariseAssignedDates`, sync POST, UI pill).
- **Freelancer Gig Edits — Bidirectional Sync**: The Gigs screen's four mutations (save, delete, status advance, show-day check-in) now push to the existing `POST/PATCH/DELETE /api/portal/gigs[/:id]` endpoints instead of being local-only, so a producer sees real-time gig progress and a freelancer's own multi-device sync becomes truly bidirectional. Each mutation is optimistic (local apply first, then async sync); atomic toggles (status, check-in, delete) revert on sync failure but only if the current local state still matches the optimistic value (guards against ghost reverts when the user clicks twice quickly or another sync interleaves). Full saveGig edits don't auto-revert (would lose user typing) but surface a dismissible amber retry banner. Brief-linked gigs are blocked from delete in the UI — the correct path is the BriefDetail decline flow which the server handles transactionally — preventing dangling `assignment.acceptedGigId` pointers. Multi-device convergence: each Gig now carries an optional `lastEditedAt`; `mergeServerGigs` keeps the local copy verbatim within a 60s freshness window, then takes server fields field-by-field afterwards (so a status change on device A actually appears on device B once the window expires). Delete races are closed by a per-PortalData `recentlyDeletedGigIds` tombstone map: a deleted gig is added with `Date.now()`, the merge function skips re-adding any server gig in the live tombstones, and expired entries are swept on every merge to keep the map bounded. Both `lastEditedAt` and `recentlyDeletedGigIds` are persisted via `normalizeGig` / `normalizeRecentlyDeleted` so a hard reload mid-sync doesn't reopen the race. All freshness comparisons route through a single `isFresh(ts)` helper that requires `age >= 0 && age < FRESH_DECISION_WINDOW_MS`, so clock skew, manual clock changes, or a tampered/cross-device localStorage payload cannot lock a row in local-authoritative mode (or suppress server re-add) forever. Files: `artifacts/rigging-load-report/src/portal/screens/Gigs.tsx`, `artifacts/rigging-load-report/src/portal/Portal.tsx`, `artifacts/rigging-load-report/src/portal/lib/portalStorage.ts`.
